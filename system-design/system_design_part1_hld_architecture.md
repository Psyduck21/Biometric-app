# Offline Facial Recognition System — Part 1: HLD & Architecture

---

## 1. Executive Summary

A **fully offline**, biometric authentication and attendance platform for React Native (Android + iOS). All inference runs on-device via TensorFlow Lite. Data is AES-256 encrypted at rest. Syncs to Supabase when connectivity returns.

## 4. Security Architecture

### 4.1 Security Layer Model (7 Layers)

```
Layer 7: Application RBAC & Session Management
Layer 6: Anti-Spoofing & Multi-Face Detection
Layer 5: Device Binding & Attestation
Layer 4: Root/Jailbreak Detection
Layer 3: AES-256 Encrypted Storage (SQLCipher)
Layer 2: Android Keystore / iOS Secure Enclave (key storage)
Layer 1: TLS 1.3 + Certificate Pinning (transit)
```

### 4.2 Cryptographic Design

```
Key Hierarchy:
  Master Key (stored in Keystore/Secure Enclave)
    └── DEK (Data Encryption Key) per user
          ├── Embedding encryption (AES-256-GCM)
          ├── Attendance encryption (AES-256-GCM)
          └── Session tokens (HMAC-SHA256)

Nonce: 96-bit random, stored with ciphertext
Tag:   128-bit GCM authentication tag
```

### 4.3 Device Binding

```typescript
interface DeviceBinding {
  deviceId: string;         // SHA-256(IMEI + AndroidId + BundleId)
  deviceFingerprint: string; // SHA-256(hardware attestation)
  boundAt: ISO8601;
  attestationCert: string;  // Android SafetyNet / iOS DeviceCheck
  userId: string;
}
```

**Binding enforcement:** Every authentication checks `deviceId` matches enrolled device. Cross-device login rejected.

### 4.4 Root/Jailbreak Detection (Multi-Signal)

> Handled entirely by `react-native-jail-monkey` — no Kotlin or Swift written.

**TypeScript (both platforms):**
```typescript
import JailMonkey from 'react-native-jail-monkey';

// Signals checked on Android:
//   - /system/xbin/su binary present
//   - Build tags contain "test-keys"
//   - Magisk / SuperSU package detected
//   - Running on an emulator
//   - App installed from untrusted source
//
// Signals checked on iOS:
//   - /Applications/Cydia.app present
//   - Suspicious files: /bin/bash, /etc/apt
//   - Sandbox write violation
//   - Symbolic links to private frameworks
//   - DYLD_INSERT_LIBRARIES injection

export function isDeviceCompromised(): { safe: boolean; reason?: string } {
  if (JailMonkey.isJailBroken()) {
    return { safe: false, reason: 'root_or_jailbreak_detected' };
  }
  if (JailMonkey.canMockLocation()) {
    return { safe: false, reason: 'mock_location_detected' };
  }
  if (JailMonkey.isOnExternalStorage()) {
    return { safe: false, reason: 'running_from_external_storage' };
  }
  if (JailMonkey.isDebuggedMode()) {
    return { safe: false, reason: 'debug_mode_detected' };
  }
  return { safe: true };
}
```

### 4.5 Replay Attack Prevention

```
Each authentication session generates:
  - sessionNonce: 128-bit random UUID
  - timestamp: Unix epoch (ms)
  - challengeHash: HMAC-SHA256(nonce + timestamp + deviceId)

Server validates:
  - timestamp within ±30 seconds
  - nonce not in used-nonce cache (TTL: 5 min)
  - challengeHash signature matches
```

### 4.6 Secure Sync Protocol

```
1. Device generates JWT signed with device private key (stored in Keystore)
2. Payload encrypted: AES-256-GCM with session key
3. TLS 1.3 transport with certificate pinning
4. Server validates JWT, decrypts, verifies device binding
5. Response encrypted + signed by server
6. Attendance records deleted locally after server ACK
```

## 5. AI Pipeline Design

### 5.1 Enrollment Pipeline

```
Camera Frame (1280×960)
        │
        ▼
[BlazeFace Detection]──── No face → Retry prompt
        │ face_bbox
        ▼
[MediaPipe Face Mesh] ── 468 landmarks extracted
        │ landmarks
        ▼
[Liveness Challenge]
  ├── Blink Detection (EAR < 0.25 for 2 frames)
  ├── Head Turn (yaw > 15° left + right)
  └── Smile Detection (lip distance ratio > 0.35)
        │ liveness_passed=true
        ▼
[Face Alignment]
  - 5-point alignment (eyes, nose, mouth corners)
  - Affine transform → 112×112 RGB crop
        │ aligned_face
        ▼
[MobileFaceNet Inference]
  - INT8 quantized TFLite model
  - Output: 512-dim float32 embedding
        │ embedding[512]
        ▼
[Embedding Encryption]
  - AES-256-GCM with DEK from Keystore
  - Store in FaceTemplates table
        │
        ▼
[Quality Check] ── Cosine similarity of 5 samples > 0.85
        │
        ▼
[Enrollment Complete] → Queue sync to cloud
```

### 5.2 Authentication Pipeline

```
Camera Frame
        │
        ▼
[BlazeFace] ──── No face / Multi-face → REJECT
        │ single_face_bbox
        ▼
[Anti-Spoofing CNN]
  ├── Texture analysis (LBP features)
  ├── Depth cues from landmarks
  └── Score > 0.85 → genuine
        │ is_live=true
        ▼
[Liveness Challenge] (random 1 of 3)
        │ challenge_passed
        ▼
[Face Alignment + MobileFaceNet]
        │ query_embedding[512]
        ▼
[Embedding Matching]
  - Load encrypted templates from SQLite
  - Decrypt with DEK
  - Cosine similarity: sim = (A·B) / (|A||B|)
  - ACCEPT if sim > threshold (default 0.65)
        │ match_result
        ▼
[Device Binding Check]
        │ binding_valid
        ▼
[Session Creation + Attendance Log]
```

### 5.3 Liveness Detection — Technical Details

#### Eye Aspect Ratio (EAR)
```
EAR = (|p2-p6| + |p3-p5|) / (2 × |p1-p4|)

where p1..p6 are MediaPipe eye landmarks (indices 33,160,158,133,153,144)

BLINK: EAR < 0.25 sustained for 2+ consecutive frames
Threshold tuned per lighting condition
```

#### Head Pose Estimation
```
Using solvePnP with 6 facial landmarks:
  - Nose tip, chin, left/right eye corners, left/right mouth corners
  
Output: rotation_vector → Euler angles
  - Pitch (nod): ±20°
  - Yaw  (turn): ±30° for challenge
  - Roll (tilt): ±15°
```

#### Anti-Photo/Video Spoofing
```
Signals used:
  1. Texture gradient (paper/screen = flat LBP histogram)
  2. Landmark jitter (static photo → zero jitter)
  3. Specular reflection pattern (screen = uniform glare)
  4. Blink consistency (video replay = pre-recorded blinks)
  5. Depth variance across face (flat = spoofed)

Decision: Weighted ensemble, threshold 0.85
```

### 5.4 Similarity Threshold Tuning

| Threshold | FAR | FRR | Recommended Use |
|---|---|---|---|
| 0.55 | 0.01% | 5% | High security |
| 0.65 | 0.1% | 2% | **Default (balanced)** |
| 0.72 | 0.5% | 0.8% | High convenience |

> Threshold stored in `Configurations` table, adjustable per deployment.

## 6. Offline-First Architecture

### 6.1 Architecture Pattern: Local-First with Sync Queue

```
All writes → Local SQLite (immediate)
              └── SyncQueue entry created (status: PENDING)

Background worker (NetInfo listener):
  Network available? 
    YES → Process SyncQueue FIFO
           ├── Upload batch (max 50 records)
           ├── Server ACK → mark SYNCED
           ├── SYNCED records → purge after 24h
           └── Server NAK → mark RETRY (exponential backoff)
    NO  → Sleep, listen for connectivity
```

### 6.2 GPS in Zero-Network Zones

```
GPS hardware works independently of network.
expo-location → uses device GPS chip directly.

Accuracy modes:
  - Balanced: ±10m (saves battery)
  - High Accuracy: ±3m (for strict geofence)
  - Passive: ±50m (ultra low power)

Offline geofencing:
  - Geofence polygons stored in Configurations table
  - Haversine formula checked locally
  - No network needed for validation
```

### 6.3 Data Consistency Strategy

| Scenario | Strategy |
|---|---|
| Duplicate attendance | Unique constraint on (userId, date, checkInTime±5min) |
| Clock skew | Device clock validated against last known NTP on sync |
| Conflict on sync | Server timestamp wins; local copy archived in AuditLogs |
| Partial upload failure | Idempotency key per record; safe to retry |
